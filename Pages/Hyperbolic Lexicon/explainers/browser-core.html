On this page you can rerun the trace parity in your own browser and put your own text through the front end.

01

Where this sits

The Python reference decides the exact claims. The browser core must reproduce it line for line before a claim decided there is shown as holding in a browser (the common rule “Authority”). Phase 2 built that core and decided the claims that compare engines. This page’s focus node is the core.

The core is one file, lexicon_core.js, with two data wrappers in data/. Around it sit the parity runner tests/parity-lexicon.cjs, the page Chromium opens, tests/l1-harness.html, the reference’s half of the run, run_claims.py --phase2 (with lexicon/phase2.py), and the Node and Chromium runner run_claims_js.cjs. Every number on this page comes from results/claims-phase2.json (the engines’ side and the decisions; summarised in claims-phase2.md), results/phase2-python.json (the reference’s side, L4(b), the reported metrics and the per-query lists; summarised in phase2-python.md), the console log phase2-console.txt, a commit message, PREREGISTRATION.md, spike S6’s output (s6_unicode_wordpiece_output.txt), results/claims.json (Phase 1), the files themselves (sizes and line counts), the core’s own source, or a rerun of tests/parity-lexicon.cjs or of the lab in chapter 4 (the per-file line counts, the 18,578/89 split and the lab’s expected counts, which the results record only as 18,667 lines in all). Where this page and those files differ, the files win.

How to read this page

supported means what the registered decision rule says, and nothing more. For L1, L3(f) and L4(a), all exact, it means every case passed and every control showed its weakness on at least one case. For L4(b) it means at least one float64 inversion occurred, and it is decided by the reference: Node’s counts are reported beside it. Chromium’s run of L4(a) on the mammals is reported, not decisive. A prediction was written with each claim; it is not part of the rule.

Timings belong to this container and change from machine to machine; this page adds “~” where it uses one.

Browser core
lexicon_core.js: one UMD module that runs the front end and the geometry in a page or in Node, a line-by-line twin of the reference’s modules, on Hyperbolic Oracles’ and the orbital core’s JavaScript loaded unchanged.
Trace parity
Regenerating each line of the reference’s trace files (reference/traces/, seeds 8000 + i, which no claim uses) from its inputs or seeds and comparing it with the reference’s line, character for character. Amendment 4 item 8 requires all of it in Node before any decisive run.
Record
L1’s unit of comparison (Amendment 4 item 2): an instance’s normalised text as UTF-8 hex, a tab, then its pieces separated by spaces, each id,start,end,hex. An instance differs in a runtime when its record’s SHA-256 differs from Python’s.
Id stream
Per instance set and vocabulary, over the instances in order: LEB128 of the number of ids, then LEB128 of each id (Amendment 1 item 2). L1 compares its SHA-256.
Cell
One vocabulary in one runtime: V0 in Node, V0 in Chromium, V1 in Node, V1 in Chromium. L1 is decided per cell.
Inversion
For L4(b): two candidates adjacent in the exact order whose exact keys strictly increase while their float64 keys strictly decrease (chapter 9).
Dry run
The runners on data no claim uses: every seed moved up by 3000, the verb forest in place of the nouns, Rng(4000 + i) strings and repository Markdown in place of L1’s instances (Amendment 4 item 7). It decides nothing.
Decisive run
The one run on the registered instances that decides: python3 -B run_claims.py --phase2, then node run_claims_js.cjs, on the code committed at a1fe9a8.

What Amendment 5 recorded

  • Disclosures. While building, the text builder timed NB and WordPiece over instance (a) in Node, and the geometry builder built all noun words and points in Node to time them: times only, nothing compared or printed. The builders and the reviewers compared the JavaScript with Python only on the Phase 1 traces, the registered dry sets and strings from unregistered seeds (70000 + i), and hashed L1’s instance lists against their pins.
  • Readings fixed in the code (each marked READING). An empty normalised text is written -, so an instance with no words has the record - TAB -; a list’s digest is the SHA-256 of its per-instance digests, each followed by LF. The decisive run refuses to start without V1 or with any trace line skipped. Control 1 is decided per runtime against the reference’s per-case SHA-256 of S6’s R(s). No UD EWT text enters a committed file. A passing L4 control 2 would void both (a) and (b). For L4(b) an infinite key takes part in comparisons, a NaN key is neither an inversion nor a tie, and non-finite keys are counted. Hugging Face agreement compares token strings only.
  • The review. Three reviewers, two skeptics for every finding, probing the core and the runners independently on unregistered data. They found no defect in NB, WordPiece or the geometry, and confirmed three gaps, all fixed before the amendment: the guard against platform Unicode missed a call made through a computed name; L1 could be decided without its V1 cells; and UD EWT text could reach the committed JSON.

The data wrappers

A page opened from file:// cannot fetch the files beside it. So make_js_data_v1.cjs writes each pinned file’s exact text into a script that registers it on LexiconData: data/unicode_15_1_v1.js (157,238 bytes, holding the 142,624-byte table) and data/vocab_v0_lex0.js (97,475 bytes, holding V0’s 55,648 bytes, one entry per line). Both sources are ASCII, so a page’s charset cannot change them. The core hashes the text again on first use and refuses it unless it is the pin. At the decisive run, make_js_data_v1.cjs --check rebuilt both wrappers and found them equal (exit 0), and both texts had their pins’ SHA-256.

V1 has no wrapper. bert-base-uncased’s vocab.txt sits in the cache, outside git, with only its hash committed. Node reads it from ~/.cache/hyperbolic-lexicon; Chromium receives its bytes from Node through the harness and refuses them unless they are the pin. In this page, V1 runs only if you give it the file (chapter 4).

The guard against platform Unicode

D5 says NB reads only the pinned table. Node 22.23.4 and Chromium 153 carry Unicode 17.0; the table is 15.1. One toLowerCase inside NB would bring 17.0 in, which is exactly what control 1 measures (chapter 6). So the parity runner reads lexicon_core.js with its comments blanked and fails if anything outside platformNormalise reaches the platform’s Unicode:

RuleWhat it catches
nameA forbidden name in the code: normalize, toLowerCase, toUpperCase, the two locale case functions, localeCompare, Intl, TextDecoder, trim, \p{, \P{, \s, \S, RegExp, String.prototype, codePointAt, isWellFormed, toWellFormed (18 in all)
literalA forbidden name inside a string, template or regex literal: a call by name, s["toLowerCase"]()
regex flagsA regular expression with the u, v or i flag (Unicode properties, Unicode case folding)
computed callAny call through a computed member, x[…](…), whose name cannot be read
string indexA computed member whose index holds a string, x["toLower" + "Case"]: a name built where it is used
indirecteval, Function and Reflect

The guard has controls of its own: a line planted for each rule must be caught by that rule, and a comment that names toLowerCase must not count. It also checks that platformNormalise is spike S6’s, verbatim. The scanner is lexical, and its comment says what lies beyond it: a name assembled elsewhere and read through a plain variable index that is not called where it is read. The core has no computed member access with a string index, no computed call and none of the indirect forms. Amendment 5’s review found the gap it had then, a call through a computed name, and it was closed before the decisive run.

The record (Amendment 4 item 2) and the id stream

Control 1: the platform’s normaliser against the table

Byte spans are [start, end) in the input’s UTF-8. Control 1 compares spike S6’s two functions on the whole string: the platform’s toLowerCase(), normalize('NFD') and removal of \p{Mn}, against the same three steps on the pinned 15.1 table. That is not NB: nothing is dropped, nothing is split into words and nothing fails closed. Your browser’s own Unicode decides the left-hand side, so what differs depends on its version.

Try it
  • The cat sat on the mat. Seven words; the full stop is a word of its own, bytes 22–23. Under V0 each word is one piece (the = 136, cat = 1057, sat = 1591, …, “.” = 17).
  • ΟΔΟΣ ΣΟΦΙΑΣ. The capital sigma at each word’s end lowercases to the final form ς (Final_Sigma), the others to σ. V0’s alphabet is ASCII, so both words are [UNK]; with V1 loaded they split into ο ##δ ##ος and σ ##ο ##φ ##ια ##ς.
  • İstanbul café naïve. U+0130 lowercases to i and U+0307, and NFD with the Mn removal strips that mark and the accents: istanbul cafe naive. V0 splits them (is ##tan ##b ##ul …); V1 keeps each whole.
  • AʕΣ (U+0041 U+0295 U+03A3). In 15.1, U+0295 is a cased letter, so the sigma is final: ς. A Unicode 17.0 platform, where U+0295 is no longer cased, gives σ. Control 1 differs here.
  • a, U+0897, b c. U+0897 is unassigned in 15.1, so NB fails that whole word closed: one [UNK] over bytes 0–5. A platform with Unicode 16.0 or later knows U+0897 as a combining mark and drops it. Control 1 differs here too.
  • 東京 tokenizer. Each CJK ideograph becomes a word of its own. V0 has neither; V1 has both.

L4(b) · Float64 is not certifiable

Round the same exact points to float64, rank by the float Lorentz product, and at WordNet’s depth the order breaks: on 997 of the 1,000 noun queries, some exactly ordered adjacent pair comes out inverted. supported (decided by the reference; Node’s counts are the same)

What an inversion is

Take one query and put the other 82,114 nouns in exact order: by exact key, then by synset offset. Walk the 82,113 adjacent pairs. A pair whose exact keys strictly increase while their float64 keys strictly decrease is an inversion; a strictly ordered pair whose float keys come out equal is a float tie, counted but not an inversion. The float key is x0·y0 − x1·y1 − x2·y2 (− x3·y3), each coordinate first rounded once to the nearest float64, then evaluated left to right in IEEE-754 double without fused multiply-add (Amendment 4 item 6). A query counts if it has at least one inversion in H³ or in H².

The first inversion

In both trees it is in the first query of the sample, 01984245 (a 25-letter word), at the very first pair of its exact order: 01982650 (24 letters), then 01983048 (25 letters). Their float keys are −1.847 × 1018 and −1.303 × 1019 in H³, and −9.04 × 1032 and −1.43 × 1034 in H²: the nearer candidate gets the larger key. The exact Lorentz product of two points on the sheet is the cosh of their distance, never below 1, so these negative values are rounding error alone. The key subtracts products that agree in their leading digits, and float64 keeps 53 bits of each.

Why H² inverts more often

H² inverts on more queries (993 against 990), with nearly twice as many inversions, and it has more inversions than H³ on 971 of the 1,000 queries (from the per-query lists). Its first inversions also come earlier: at 9 letters at the shortest, and at 12 letters or fewer on 111 queries against H³’s 11. A likely reason, which the run does not measure: each letter boosts by a factor of 12 in D3’s H² tree (t = 11/13) against 7 in the H³ tree (t = 3/4), so at the same word length the H² coordinates are larger (in Phase 1, at most 252/142 bits per coordinate against 184/102), and the key’s cancellation throws away more of float64’s 53 bits. The first inverted pair fits that reading: the same two synsets get float keys near 1033 in H² and near 1018 in H³. H³, for its part, has far more float ties (152,072 against 1,715); the results do not say why.

The registration predicted (b) from spike S1, which saw float64 first invert at depth 10 on straight paths and 12 on random words, in H³ (Explainer 8). On the nouns, the earliest first inversion in H³ has an 11-letter deeper word.

10

What this does not show

Four exact results, on one machine, about one front end and one geometry. That is narrower than it may sound.

  • Three engines, one machine. Python 3.13.18, Node 22.23.4 and Chromium 153.0.8010.12, on this container (linux x64). Not Firefox, Safari or another browser engine, not another operating system or processor, not another version. The pinned table is meant to make the platform’s Unicode irrelevant, and control 1 shows that it would otherwise matter; another engine is a new test.
  • Byte identity, not tokenizer quality. L1 says the same bytes, pieces, ids and offsets come out everywhere. It says nothing about how good V0 or V1 is. V0’s alphabet is ASCII, so under V0 any word with a non-ASCII letter is [UNK], identically in every engine.
  • Hugging Face is reported. Its agreement compares token strings only and decides nothing; its 28 and 29 differences are explained here only through the examples the results keep.
  • L4(a)’s reach. On the nouns it uses queries 0–199 of the sample, each against all 82,114 other nouns; Python and Node are the decisive pair, and Chromium ran only the mammals, reported.
  • L4(b) is about this float formula. It shows that rounding these exact points to float64 and evaluating the Lorentz product left to right cannot be trusted to keep their order. It does not test other float formulas or learned embeddings: L4(c), on L6’s learned tables snapped to the 2−32 grid, was decided in Phase 4: supported, with the largest change in MAP 9.37×10−6 (Explainer 12).
  • The guard is lexical. It reads the core’s source, not its behaviour; what it cannot see is stated in its comment (chapter 3). The behavioural evidence is L1 itself: 725 cases on which the platform differs, and 0 on which the core does.
  • The labs on this page run the trace lines that need neither WordNet nor V1, and the front end on your own text. They demonstrate the core in your browser and decide nothing.
  • Timings belong to this container. Every “~” number would move on another machine; no claim here is decided on time (L11, in Phase 3, was: Explainer 11).
11

Phase 3, planned and done

The plan at the end of Phase 2: records and biochains, that is, the synchronous grower in JavaScript and Python, the records, RFC 6962 manifests, the exact weave and the hardened, attested importer, to decide L8–L11. Phase 3 has built them and decided all four (Explainer 11).

  1. L8 · Language shards are Owl-valid biochains. Our JS grower (the biochain_v1.js codec with the orbital core’s SHA-256) and a Python port must each give, field for field, the record Owl Academy’s own growBiochain gives, on C0’s 148 shards and 20 synthetic shards; Owl’s and BioChain-AI’s verifyIntegrity must accept every record; and the derived layers (the V0 id stream and its SHA-256, addrTableRoot) and the LPREP/1 strings must be identical in Python and JS. The id stream there is the function L1 has just compared (the records in Explainer 4).
  2. L9 · The corpus manifest and the exact weave. LCORPUS/1 as an RFC 6962 tree over the shards, with inclusion proofs, consistency proofs (LGROW/1 append-only) and every registered alteration detected; each shard’s exact norm-5 weave (the manifest, the weave).
  3. L10 · The hardened, attested import. In JS (WebCrypto) and Python, 50 clean attested records accepted and 450 tampered ones in nine classes rejected, naming the failing check, with identical verdicts in both languages (verification).
  4. L11 · Verification is cheap enough. A full C0 shard verified with every hardened check in a median of at most 250 ms in Node, single-threaded, on this container.
What Phase 3 found

Amendment 7 fixed the definitions before any code. The chain section of lexicon_core.js and its Python port in reference/lexicon/ were then built (a container restart cut the first build off; the work on disk was kept and committed, b822237), reviewed and dry-run, and Amendment 8 was written before the decisive run. Parity first: tests/parity-lexicon.cjs, now with the chain trace, passed 19,991 of 19,991 lines. Then one decisive run, on the code committed at 6da04be, 50 min 44 s long. L8 is supported for the JS grower and the Python port: 0 of 336 records differ from Owl Academy’s own growBiochain in any of the fifteen fields, and the V0 id stream that L1 compared is identical in Python and JS on every shard. L9 is supported: every root and proof is equal in JS and Python, every alteration is detected, and all 148 exact weaves are exact. L10 is supported: 0 false accepts and 0 false rejects of 500 attested packages in each language, with identical verdicts. L11 is supported: a median 155.4 ms per full C0 shard, 95% interval [154.2, 156.0], against the 250 ms bar, on packages grown with engrams off, a reading Amendment 8 fixed after dry runs had put the engrams-on median at 243.5–265.5 ms (in the decisive run, engrams-on packages took 243.6 ms, reported). Every control showed its weakness, L11’s as Amendment 8 replaced it.

Then Phase 4 decided L6 and L4(c) (learned embeddings, with L6’s protocol as Amendment 6 attributes it), all supported, L6(c) against its registered prediction (Explainer 12), and Phase 5 brings the 2D and 3D pages (the roadmap).
