The Shared Cores

Before anything could be built on the orbital calculators, their exact code had to exist somewhere other than inside the pages. Phase 1 moved it into one module that the pages are still built from, byte for byte, and made Hyperbolic PolyStep’s exact modules importable without torch.

01

Where this sits

The shared cores take the tier laws, the triple quad, the gauge and the pump from the orbital calculators and feed the Python reference of Phase 2.

02

Why a module

The four orbital pages, Galactic Lensing Part 1, the Tri-Engine Soliton, Tri-Engine Convergence and the Zero-Point Tri-Engine, are generated from templates in scripts/geometric-build/. Their exact code lived inside those templates: the tiles and the Merkle chain in Part 1’s, the tier frames and the TQF in Part 2’s, the gauge and memory repair in the Convergence template, and the pump inside gen4.py.

That was fine for the pages, which the build stitches together. It left nothing another system could load. In Phase 0, Spike C had to cut functions out of the templates by name, which breaks the moment one is renamed. Decision D2 chose the other way: move the code into one module and have the build write it back.

04

How the build works now

A segment runs from // @orbital-begin name to // @orbital-end name in the module. Where it used to be, the template now holds /*__ORB:name__*/.

  • Expand first. orbital_segments.py writes every segment back into every template before build.py splices or gen4.py patches, so their string searches find what they always found.
  • One patch remains. gen4.py still edits the readout segment for the Zero-Point page, giving the readout its pairing node k. The module keeps the Convergence version, with node 29.
  • Nothing else outside the segments. The module adds only its wrapper, the export list and a neutral state: in the pages state is each page’s live controls; in the module it is tension 0, torsion 0 and coupling κ = 1, the settings claim E6 specifies.

How the browser tests ran here

They need local copies of Three.js r158 and r128 and of KaTeX, which the CDNs serve. The CDNs are blocked in this sandbox, so the same releases came from the npm registry (three@0.158.0, three@0.128.0, katex@0.16.9). The build README now lists all of them.

06

Using it

The module is UMD: a global in a browser, require() in Node. There is no build step and no dependency.

<script src="../../../scripts/geometric-build/orbital_core.js"></script>
const { Fraction, packTile, merkleChain, gaugeExact, readout, pumpOf } = window.OrbitalCore;

// Node
const O = require('./scripts/geometric-build/orbital_core.js');
O.state.kappa = 0.5; // read the pages' functions under other settings

Changing shared code now means editing the text between a segment’s two markers and rebuilding: every page that uses it changes, and so does every system that loads the module. tests/rebuild-identical.sh then says which pages moved.

08

PolyStep without torch

The engram reference will use Hyperbolic PolyStep’s exact modules in place: the generator, the exact rationals, the 3D decoder and its tree, frames, the coupler and the fence. Until now, importing any of them imported torch, because the package’s __init__.py loaded the step.

Decision D7 made the step load lazily (PEP 562): PolyStepH, StepConfig and StepState import torch and polystep the first time they are used, and nothing else does. Every name the package exported before is still there, and hpstep.step still resolves. The suite ran in a fresh environment with torch 2.15 and polystep 1.1.1 from PyPI, and in a second one with numpy and pytest only.

09

Smaller changes

  • scripts/geometric-build/core.js is gone; its text is the module’s core segment. The build README and the Hyperbolic Oracles build explainer name the module instead.
  • Spike C now requires the module rather than cutting functions out of the templates. Its nine checks give the same results; only its title line changed.
  • tests/idx.cjs read Three.js r128 from a folder of an earlier session; it now reads it from $SP, like the other tests.
  • PolyStep’s run_traces3d.py opened twin3d.json for writing before computing the trace, so a run that failed (now possible without torch, which the twin half needs) left the file empty. It now computes first, and the trace it writes is unchanged.
