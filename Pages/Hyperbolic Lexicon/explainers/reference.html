01

Where this sits

The preregistration says what is tested and how it is decided. The Python reference is the code that decides the exact claims, and the browser core must reproduce it; Phase 2’s core does, line for line (Explainer 10). This page’s focus node is the reference.

The reference lives in reference/: the package reference/lexicon/, the runner run_claims.py, the pins in golden/, the traces in traces/ and the results in results/ (reference README). Every number on this page comes from results/claims.md (the same content as claims.json), its console log claims-console.txt, a commit message, PREREGISTRATION.md, or the pinned files’ own meta files and headers. The JSON gives exact metrics as rationals next to their floats; this page rounds the float. Where this page and those files differ, the files win.

How to read this page

supported means what the registered decision rule says, and nothing more. For an exact claim it means every case passed and every control failed. For L5 it means four bootstrap intervals lay above 0 on both instance sets. A prediction was written with each claim; it is not part of the rule, and a prediction can be wrong while its claim is supported. That happened once, on L2.

Timings belong to this container and change from machine to machine; claims.json marks L3’s millisecond timings “~ms” and gives every claim’s and arm’s seconds unmarked; this page adds “~” where it uses one.

Python reference
The code that decides the exact claims (the common rule “Authority”). It imports Hyperbolic Oracles’ hpstep and Engram Mind’s Eye’s engram modules in place, unchanged.
Dry run
The runner on data no claim uses: every seed moved up by 3000, the verb forest in place of the nouns, repository Markdown in place of the lemma types, and q = 13 only (Amendment 1, item 10). It decides nothing.
Decisive run
The one run on the registered instances that decides. Here: python3 -B run_claims.py, on the code committed at 88e63f7.
Pin
A file fixed by its SHA-256 and size. The reference refuses to load a pinned file whose hash differs.
Trace
A file of inputs and the reference’s outputs that the browser core must reproduce line for line. Traces use seeds 8000 + i, which no claim uses.
Paired AP difference
For each query, its average precision in one arm minus its average precision in another. L5 decides on the mean of these differences and its 95% percentile bootstrap interval (10,000 resamples, seed 7).

Why the definitions came first

The registration fixed the claims, but some things it named had no algorithm yet: how V0 is trained, how a vocabulary entry gets an address (map A), how tied candidates are listed. Others needed a reading before code could be written: what a lemma “type” is after normalisation, how the flat arms keep the trees’ directions, how S3’s permutations are drawn, which bootstrap computes the intervals. Writing all of this down before any module existed means none of it could be chosen after seeing how the code or the data behaved. Amendment 1 changed nothing registered; where a reading could be taken for a change, it gives the reason.

The reference then had to decide some smaller readings in code (an invalid-UTF-8 offset, the trivial eigenvalues, how distortion treats two synsets with one word). Each is marked READING in its code and listed in Amendment 2, which was committed before the decisive run.

Dry runs, then one decisive run

The registered dry run (Amendment 1, item 10) uses the same runner on data disjoint from the instances: seeds 4000 + i and 5000 + i, the verb forest with its 559 roots under a virtual root, the repository Markdown spike S6 used in place of the lemma types, and q = 13 only for L7. It ran after the geometry track and again after the fixes. Its outputs decide nothing, whatever labels they carry. Then run_claims.py ran once on the registered instances, and its output was committed as it came out.

Checked twice before it counted

Before the decisive run, each track had an adversarial review: four reviewers, and two skeptics for every finding. Amendment 2 records that they worked by independent reimplementation, on unregistered data. Amendment 3 corrects that for the text track: its checks compared the Python NB and WordPiece with Python oracles over L1’s instances (a)–(c), and retrained V0 on (a) as registered. That is not L1’s metric, which compares runtimes, and it decided nothing.

The text-track review

Rebuilt independently: a naive V0 trainer rebuilt V0 byte for byte. An independent NB oracle agreed on every L1 instance and on 6.7 million code-point contexts. WordPiece agreed on every instance, for V0 and V1. No mismatch. (These L1 instances were not a decision: L1 compares the reference with Node and Chromium, which Phase 2 did; Explainer 10.)

Confirmed and fixed (20c3320): traces_text.py --check skipped the whole check when V1 was not cached; it now always compares the normaliser trace and the V0 lines. The guard against platform Unicode now covers every Unicode-dependent str method, called or referenced, in normalise, unicode_tables and wordpiece. L1’s four instance lists were pinned. make_unicode_v1.py --check compares the whole meta. bert_oracle.py states which control-character rule it follows.

The geometry-track review

Rebuilt independently: trees in Fractions, the flat arms, pessimistic ranking, the id codec and L7. They agreed without a mismatch, and the review found no code defect.

Confirmed and fixed (8d845c7): the integer decoder’s test used only tree points; it now runs on real off-tree points with forced ties. The runner’s L7(e) control was mislabelled: the registered control (doubled-coordinate products not divided by 2L) is now a module function with its own test, and the runner uses it; the product without SHD-CCP’s final halving stays as a reported second control. Map A reads NB punctuation from the pinned table, not from the interpreter. The H² denominator test covers n = 1–6, as its docstring says.

Amendment 2 sums up what the reviews confirmed as gaps in tests and pins; in every rebuild, the independent code agreed with the reference. All fixes were committed, and the dry run was repeated on the fixed code, before Amendment 2 and before the decisive run.

Amendment 2: a disclosure and an erratum

A disclosure

While the geometry modules were being written, a builder’s timing script ran L3’s certify and the prefix check of L3(d) over all 82,115 noun words, to measure their cost. In Amendment 2’s words: “Its outcome was neither reported nor looked at, and no code was changed after it.” Both checks are exact, deterministic and all-or-nothing, with nothing to tune, and the decisive run recomputed them. It is recorded under the common rule “Reporting”.

An erratum

Amendment 1 said in a parenthesis that “BERT drops every C category”. That is wrong for google-research/bert, whose _is_control drops only Cc and Cf; it is Hugging Face transformers’ copy of the BasicTokenizer that drops every C category. The rule in force does not change: NB drops Cc, Cf and Co, and keeps Cn so that a token holding an unassigned code point fails closed. It is the stated rule, and no L1 instance contains a Co code point. Explainer 3’s Phase 0 text, “Cc, Cf”, described google’s BERT; it now states the rule in force, as Amendment 2 said it would.

Amendment 2 also lists the readings fixed in the code (for instance: L3’s truncation control gives every child one letter, the digit min(k, 4); a query without graph-edge neighbours is left out of the paired differences and counted, and there were none among the nouns or mammals; L7’s trivial eigenvalues are the top of the spectrum and, for a bipartite graph, the bottom). Nothing registered was changed.

L2 · engram/1 is not a token id

The share is 52.6%, far above the 1% the claim needs, and the control gives no collision, so L2 is supported. In plain terms, more than half of WordNet’s lemma types cannot be told apart from some other type by their engram/1 key.

Why so many: the key keeps only parity

crystallize in ttmpt_core_v1.js upper-cases the text, skips every character that is not A–Z, and XORs a fixed 64-cell pattern for each remaining letter into an accumulator. So letter order does not matter, every non-letter is ignored, and a letter that occurs twice cancels itself. The key depends only on which letters occur an odd number of times.

  • The zero key holds every type in which each letter occurs an even number of times, and every type without letters. Its first entries, sorted: “. 22”, “0”, “1”, “10”, “100”, “1000”, … (NB splits punctuation into words of its own, so the lemma .22 becomes the type “. 22”). Any type like “noon”, with every letter twice, lands there too.
  • Anagram classes share a key because they have the same letters. Two from claims.json: “' hood” and “hood”, which differ only in an apostrophe; and a class of 14 that runs from “. 22 caliber”, “. 22 calibre” and “. 38 caliber” to “caliber” and “calibre”: digits and punctuation do not count, and caliber and calibre use the same letters.
  • Parity classes go much further. The key cannot tell “tot” from “o”: the two t’s cancel. Any two types with the same set of odd-count letters collide, whatever their other letters.
The registered prediction was wrong

L2’s prediction read: “Supported, with a share between 2% and 10%: anagram classes (dog/god), words in which every letter appears an even number of times and numerals (all on the zero key), and types that differ only in non-letters.” The share is 52.6%, five times the top of that band.

The prediction named the right mechanisms but not the main one. The anagram classes, which already include the numerals and the types that differ only in non-letters, hold 15,025 types: 10.2%, about the band’s top. The other 62,495 types in shared classes (77,520 − 15,025) share a key with types made of different letters, because the key keeps only the parity of each letter’s count. The prediction counted anagrams and the zero key, and missed that any two types with the same set of odd-count letters share a key. The decision does not depend on the prediction: the rule asks for at least 1%, and the miss is reported as a miss.

What L2 does not say: engram/1 keeps its role as a checksum and as Engram Mind’s Eye’s compatibility key (D4). The Lexicon’s token ids come from the vocabulary, and its addresses from the L3 rule (ids in Explainer 3).

L3 · An exact address for every noun

Under the L3 rule every WordNet noun synset gets a reduced word in the norm-5 tree, and every word an exact point in H³ and in H². All 82,115 pass every part decided in Phase 1. supported (Python side: (a)–(e) and (g))

The rule (Explainer 3): the spanning parent is the first @ or @i pointer; entity.n.01 sits at the word [0]; children are ordered by synset offset; child k of a node with c children takes m = max(1, ⌈log₅ c⌉) letters, the base-5 digits of k.

Floats do not survive WordNet’s depth: 95% of the words longer than 12 letters fail to decode, as spike S1 led the registration to expect. The registration said that a larger minority of noun words than of verb words may pass 25 or 27 letters, and that the share would be reported. It is 9.1% beyond 25 letters (7,485 words) and 4.3% beyond 27 (3,565), against 0.04% and none for the verbs in spike S3. Part (f), decided in Phase 2

L3(f) asks whether Python and JavaScript give the same words and points. Phase 1 wrote the Python side: the canonical point list of all 82,115 nouns (one line per noun and tree, every coordinate in lowest terms) has SHA-256 eb22bf00689ec86da05f0f4ba6338abc0ba0a1549ada844a134cbce154a3ebc6, and the 2,000 sampled nodes, node i = Rng(1000 + i).below(82115), are written line by line in results/l3f-python.txt. This package’s H³ points equal hpstep’s point_exact on all 2,000. The browser core had to give the same hash and the same lines. In Phase 2 it did: Node’s canonical point list has this SHA-256 and all 2,000 lines are equal, so L3(f), and with it L3, is supported (Explainer 10).

07

L5 · Hyperbolic against flat

Does the training-free exact tree reconstruct the noun hierarchy better in hyperbolic space than the same construction at curvature 0? At d = 2 and 3, on both instance sets, by the registered rule: yes. supported

The arms and the rule

  • H3, H2: the exact trees of L3, ranked by the exact Lorentz product.
  • F3, F2: the same words, directions and step rule in R³ and R² with unit edges, ranked by exact squared distance. F3*, F2*: a flat fractal tree, the same directions with edge length (1/4)k into a word of k + 1 letters.
  • S3 (control): H3 with words shuffled among synsets of equal word length, 20 permutations on the mammals and 5 on the nouns. K3 (control): content-hash words, engram_core.encode of the first 8 bytes of SHA-256 of the first lemma, 28 letters each.
  • Instances: the 1,176 synsets of the mammal spanning subtree, each a query against the other 1,175; and the 1,000-query noun sample, each against the other 82,114.
  • Metric: graph-edge MAP (the neighbours are the spanning parent and the children), pessimistic ties. Closure MAP, mean rank, distortion and bits are reported. The effect is the mean paired AP difference with its 95% bootstrap interval.
  • Decision: supported if the intervals of H3 − F3, H3 − F3*, H2 − F2 and H2 − F2* all lie above 0 on both sets; refuted if any lies entirely at or below 0; inconclusive otherwise. Controls: the intervals of H3 − S3 and H3 − K3 must lie above 0 on both sets, or the metric cannot see hierarchy and the test is void.

Every arm, both sets

MAP and distortion are rounded to 4 decimals; mean rank pools every (query, neighbour) pair. For S3 the graph-edge MAP is the mean over permutations and the other columns give the range over permutations. Distortion is registered for H3, H2, F3 and F2 only, and bits for the six construction arms.

What it means, and what it does not

  • It means that, given the same words, directions and step rule, the hyperbolic tree ranks each synset’s parent and children ahead of the other synsets better than either flat construction does, at d = 2 and d = 3, on the mammals and on the nouns, by an amount the bootstrap resolves.
  • F3* comes close. The flat fractal tree, whose edges shrink by 1/4 per letter, reaches 0.6420 against H3’s 0.6907 on the mammals and 0.5001 against 0.5679 on the nouns. The margins, 0.049 and 0.068, are small, but their intervals ([0.042, 0.055] and [0.062, 0.074]) lie clearly above 0. Its graph-edge mean rank is ten to thirteen times H3’s (28.88 against 2.91; 79.44 against 5.94), which suggests that the neighbours it does not rank near the top fall far down the list.
  • H2 slightly beats H3 on graph-edge MAP (0.7187 against 0.6907 on the mammals, 0.5901 against 0.5679 on the nouns), with lower distortion, while its graph-edge mean rank is lower on the mammals and higher on the nouns. No comparison between H2 and H3 was registered and no interval was computed for it, so this is an observation, not a finding.
  • Closure MAP is much lower: 0.1577 (H3) and 0.1567 (H2) on the nouns, about 0.31 on the mammals. The closure protocol counts every ancestor and every descendant as a neighbour, and a distance-based tree is likely to put distant ones farther away than nearby siblings and cousins (an explanation, not measured here). The closure numbers are reported and decide nothing; they are never compared with graph-edge numbers (the two protocols in Explainer 7).
  • Sala et al.’s 0.989 is not reached. The registration reports the nouns’ graph-edge MAP against Sala et al.’s combinatorial 0.989 in 2 dimensions at about 500 bits, and predicted that this rule falls short. It does: 0.5901 in H2 and 0.5679 in H3, on the 1,000-query sample. The expected cause is the virtual letters: under a node with more than 5 children, siblings that share a virtual prefix sit as close as the parent or closer (spike S3 on verbs: 0.9974 on one-letter edges, 0.32–0.43 on longer ones; Explainer 8). This comparison is not part of L5’s decision (baselines in Explainer 5).

The same reduced word is an address, an exact H³ point and a vertex of SHD-CCP RFC 03’s LPS Ramanujan graph X(5, q). For q = 13, 17 and 29 every exact part holds and the spectra are Ramanujan. supported

A shard key, never integrity

The vertex of a word is a cheap, well-spread key: every vertex is hit at q = 13 and 17, and all but 13 at q = 29, with the largest load at most twice the even share at q = 13 and 17 and under three times at q = 29. But words longer than r share vertices, and must, since 82,115 words land on at most 12,180 of them. LPS Cayley hashes also have known collision attacks. So the registration fixes the reduction as a shard key, never as an integrity check; integrity comes from SHA-256 and RFC 6962 manifests (Explainer 2, the RFC 03 proposal).

09

What this does not show

Three claims, and L3 on its Python side, are decided in Python, on WordNet. That is narrower than it may sound.

  • Nothing about language models. No claim here is about an encoder, pretraining or a downstream task. Stage-2 to Stage-4 claims are registered by amendment before any code for them (Explainer 7).
  • Only the Python side. The common rule says the browser core must reproduce the reference’s traces line for line before a claim decided in the reference is shown as holding in the browser. Byte identity across Python, Node and Chromium (L1), the same words and points in JavaScript (L3(f)) and identical exact rankings across engines (L4(a)) compare the reference with lexicon_core.js; L4(b), the float64 test on noun queries, was decided with them in Phase 2 (Explainer 10).
  • One sense per synset, one parent per node. An address is one synset in the spanning tree, without context. The 2,213 nouns with several parents keep only their first @ or @i parent in the address (closure MAP still counts every ancestor). ## pieces get orthographic addresses (map A).
  • L5 is against the same construction at curvature 0. It is not a comparison with learned embeddings (L6, Phase 4) or with published systems, it is decided on graph-edge MAP, and on the nouns it uses a 1,000-query sample.
  • L7(d) is numerical. The spectra are float64 eigenvalues with a margin of at least 10−9, which the smallest margin, 0.030120, clears by far; the exact parts (a), (b), (c) and (e) are checked case by case.
  • L2 is about token ids only. engram/1 keeps its role as a checksum. And V0’s alphabet is the 64 ASCII code points of the glosses, so under V0 a word with a non-ASCII letter is [UNK]: a limit of V0’s coverage, which does not bear on L1’s byte identity.
  • Timings belong to this container. Every “~” number would move on another machine; no claim in Phase 1 is decided on time.

Phase 2, planned and done

The plan at the end of Phase 1: the browser core, lexicon_core.js, on the shared cores unchanged, would reproduce the reference’s traces line for line, and then decide L1, L3(f) and L4(a, b). Phase 2 has done both (Explainer 10).

  1. Reproduce the traces. The normaliser on 388 cases, WordPiece under V0 and V1 with both id-stream SHA-256s, the letter rule and the verb forest, 300 words’ exact points in every arm, and 20 queries’ rank lists and APs (chapter 3), as the common rule “Authority” requires.
  2. L1 in Node and in headless Chromium: identical normalised bytes, tokens, ids, byte offsets and id-stream SHA-256 against the reference on all four instance lists (117,659, 16,622, 20,520 and 2,000 strings), for V0 and, now that it is pinned, for V1. Its controls: the platform’s own normaliser, shortest-match WordPiece and accent stripping off must each differ (Explainer 3, Stage 0 in Explainer 7).
  3. L3(f): the same canonical point list SHA-256, eb22bf00…54a3ebc6, and the same 2,000 sampled lines.
  4. L4(a): identical rank lists, and MAP and mean rank equal as exact rationals, in H³ and H², on the mammals and noun queries 0–199. L4(b): a float64 inversion of an exactly strictly ordered pair on at least one of the 1,000 noun queries. L4’s controls: float32 ranking must invert, and an acosh evaluator with index tie-breaking must differ where exact ties exist.
What Phase 2 found

Parity first: tests/parity-lexicon.cjs passed 18,667 of 18,667 lines in Node, 18,578 of them reproducing the five traces of chapter 3. Then one decisive run, on the code committed at a1fe9a8. L1 is supported in all four cells (V0 and V1, each in Node and in Chromium): 0 of 156,801 instances differ, and every id-stream SHA-256 is equal. L3(f) is supported: the canonical point list has the SHA-256 above, and all 2,000 sampled lines are equal. L4(a) is supported: every rank list and every exact MAP and mean rank is equal in Python and Node. L4(b) is supported: float64 inverts an exactly ordered pair in 997 of the 1,000 noun queries. Every control failed as required. The whole account is in Explainer 10.

Then Phase 3 decided L8–L11 (shards, manifests, the hardened importer, verification time), all supported (Explainer 11), and Phase 4 decides L6 and L4(c) (learned embeddings) (the roadmap). The network is wider than in Phase 0: huggingface.co is reachable, which is how V1 was pinned, while osf.io file downloads still are not; BabyLM is also published on Hugging Face.
