SHD-CCP: Three Layers, Eight Layouts, One Bridge

SHD-CCP is the 64-bit protocol in which Owl Academy and BioChain-AI write their text chains. It exists in three layers that disagree: a specification, the code that actually runs, and prose. This page sorts them out. It shows eight incompatible ways to read one 64-bit word, and lets you try them. It fixes the one place where the Lexicon speaks SHD-CCP. And it follows the one deep link: our address tree is the tree that SHD-CCP’s planned Ramanujan overlay is built from.

01

Where this sits

The focus node is the working SHD-CCP: the 64-bit word and the stream that Owl Academy and BioChain-AI actually write. It is the one part of SHD-CCP the Lexicon must match byte for byte, because every language shard it grows has to verify in their code.

Phase 0 is analysis, measurement spikes and a preregistration; there is no model code. This page rests on a read-only survey of four repositories (Ebayednoob 7b10514, Owl Academy 7f45f35, BioChain-AI c975161, SHD-CCP 97d90ac) and on its adversarial cross-check, whose corrections win. It also uses the design spec, the documents in proposals/ and the spikes.

The spikes S1–S7 have finished. They ran before the preregistration, on data disjoint from every registered instance, and they decide no claim. This page quotes their numbers exactly as the captured outputs print them, and calls them spike results; S4, S5, S6 and S7 matter most here (outputs: S4, S5, S6, S7; Explainer 8 has all seven). Lines the outputs mark with “~” are timings or facts about this container (Node 22.23.4, Python 3.13.18, 4 CPU cores), and are quoted as such.

How to read the marks

exact: integers, rationals or bytes, identical in every engine. float: floating point, rounded at every step. Claims L1–L11 are registered in PREREGISTRATION.md; none was decided when this page was written, and Phase 1 has since decided L2, L3’s Python side, L5 and L7 (Explainer 9), Phase 2 L1, L3(f) and L4(a, b) (Explainer 10), Phase 3 L8–L11 (Explainer 11), and Phase 4 L6 and L4(c) (Explainer 12), all supported. Where this page names a claim, it says what the claim tests, not what it found.

SHD-CCP
The Symbolic High Dimensional Context Compression Protocol. Its repository calls it a hardware-level interface in which every token is one 64-bit word.
Word, tile
A 64-bit integer. SHD-CCP calls it an “Einstein tile”; the name refers to no tiling geometry in the code. Bit 0 is the least significant bit, so “63..60” means the top four bits.
Layout
Which bits mean what. The same 64 bits read under two layouts give two different sets of fields.
Form
A 4-bit field (a nibble: 16 values) meant to say what the rest of the word holds. Where it sits depends on the layout.
Parity bit
One bit set so that the word holds an even number of 1 bits. It catches any odd number of flipped bits, and no even number.
Biochain
Owl Academy’s and BioChain-AI’s record of one text of at most 60,000 bytes: an shdccp/2 stream that rebuilds the text exactly, plus hashes that commit to it.
Merkle root
One hash that commits to a list: hash each item, then hash the hashes in pairs, level by level, down to one value.
LPS, Ramanujan
Lubotzky, Phillips and Sarnak built regular graphs that spread out as fast as a regular graph can. For a 6-regular graph, Ramanujan means every eigenvalue other than ±6 has size at most 2√5 ≈ 4.4721.
02

Three layers that disagree

The SHD-CCP repository pitches a hardware-level interface in which every token is a single 64-bit word. In practice the name covers three layers. They do not agree with each other, and only one of them runs.

1 · The specification

A spec scaffold. RFC 01 drafts the tile (Form at 36–39, “layout NOT frozen”) in six bindings: Python, JavaScript, C, Rust, Java, Elixir. The Kernel Ontology puts its Form header at 60–63 and records the clash as an open decision.

BioChainAI/SHD-CCP @ 97d90ac

2 · The working SHD-CCP

The Blackwell 64-bit word inside the shdccp/2 stream, with hashes and ECDSA attestations. Engram Mind’s Eye pins it verbatim. None of this code is in the SHD-CCP repository; its manual only describes the word, as the “Blackwell Block”.

Owl & BioChain-AI biomesh.js · shdccp_kernel.py

3 · Prose only

LPF-128 (a 32-bit header, the 64-bit core and a CRC32 footer), Falcon-512 chaining, and the Fokker–Planck sieve. No CRC32 or Falcon code exists; the manual itself flags the sieve as conjecture.

Governance against practice

SHD-CCP’s ecosystem README calls geometric-engine-spec the “single source of truth” that BioChain consumes. The real BioChain-AI and Owl Academy code ignores it: it uses a different layout and no SHDGEV01 vectors. (A small BioChain-AI scaffold inside the SHD-CCP repository marks Merkle commitment as a TODO; the real BioChain-AI repository implements Merkle roots.) Nobody is named as the owner of the RFC 01 against Blackwell decision. The layout census asks SHD-CCP to settle it.

What the Lexicon takes from each layer. From the specification: the Ontology’s kernel pipeline (for kernel 0xA, chapter 7), HurwitzQuaternion as a cross-check, SHDGEV01 for golden vectors, and RFC 03’s X(5, q) slot. From the working layer: the Blackwell word and shdccp/2, unchanged, at the bridge only (chapter 6). From the prose: nothing.

The working SHD-CCP

What runs is the Blackwell word inside the shdccp/2 stream. It lives in Owl Academy’s scripts/biomesh.js, in BioChain-AI’s src/biomesh/biomesh.js and protocol/shdccp_kernel.py, and in Engram Mind’s Eye’s verbatim pins.

The check word 9841D88D8B003CEA is what crystallize gives for the 60 bytes 0, 1, …, 59. Owl Academy, BioChain-AI and Ebayednoob all pin it. Its fields read back as they should: a chunk length of 60, and a checksum of 29·8 + 2 = 234, which is 0 + 1 + … + 59 = 1,770 modulo 256. The 32 middle bits are a 64-bit fold of the bytes, folded again to 32.

Three readings of the same 32 bits

SHD-CCP’s manual calls the quaternion field “FP4”. BioChain-AI’s Python kernel reads four int8 codes, value = code/127, with −128 forbidden. A crystal packet holds raw hash bits, and the weave reads them again as a float quaternion (crystalQuat). All three readings live in the code. The second one causes the 0x80 divergence of chapter 8.

The shdccp/2 stream

  1. Cut. UTF-8 text of at most 60,000 bytes (MAX_GROW_BYTES, the budget of one Firestore document) is cut into 720-byte chunks.
  2. Code. Each chunk goes through an order-2 rank coder that starts fresh for every chunk. Each byte is written as its rank, by frequency, among the bytes already seen after the same two bytes, in Elias-gamma code. A byte not seen there yet gets the next rank as an escape, followed by its 8 raw bits. It is lossless by construction.
  3. Crystallize. Each chunk also becomes one form-9 Blackwell word: payload16 holds the chunk length, freq and amp the checksum, and parity is set last.
  4. Frame. A frame is the 16-hex packet, an 8-hex (32-bit) residual length in bytes, and the residual. The frames are joined into one hex string, the stream, marked streamVersion: "shdccp/2".
  5. Commit. Leaf i is SHA-256 of the string i + "|" + SHA-256(chunk), both hashed over strings (the exact rule is in chapter 8). The leaves are hashed in pairs, level by level, into a Merkle root; on a level with an odd count the last node is duplicated.
  6. Weave. Each chunk’s crystal also gives a unit quaternion. Their ordered product, renormalised after every step with Math.hypot and written with 12 decimals (toFixed(12)), is the chiral weave float. A mirror weave runs over the conjugates in reverse order.
  7. Name. chainId = “BC-” and the first 24 hex digits of SHA-256(merkleRoot + “|” + weaveChiral). An optional engram layer adds 64 bits per word token.
  8. Sign. In BioChain-AI, publishing signs the commitment GROWN/1|chainId|merkleRoot|weaveChiral|weaveMirror|origBytes as an ATTEST/1 attestation: ECDSA P-256 over ATTEST/1|keyId|keyVector|SHA256(commitment)|epochToken, checked against a key registry. A new epoch also signs a GROWTH/1 commitment. Owl Academy signs the same commitments with a Minor Tome seal: ECDSA P-256 over SEAL/1|sealId|sealVector|SHA256(commitment)|tickToken.

Codices travel in the same word: a codex stream opens with GEAR (form 1), carries PRIME entries (form 2) and closes with HALT (form 0), a closed instruction set.

Measured. Spike S4 grew all 55 WordNet verb and adjective gloss shards, and 8 synthetic ones, with a spike-only synchronous grower built from biochain_v1.js and the orbital core’s SHA-256. Field for field, it gave the record of Owl Academy’s own growBiochain on 126/126 records, with engrams on and off. Owl’s verifyIntegrity accepted every engrams-off record (63/63). What verifyIntegrity checks, and what it does not

Owl’s verifyIntegrity checks, stopping at the first failure: packet parity, decoding, each leaf, the rebuilt Merkle root, the chiral weave, then the engram layer recomputed from the text. But leaves and root are checked only when present. A packet’s crystal and checksum are never compared with the rebuilt chunk. chainId and the mirror weave are not recomputed. So it proves self-consistency, not authenticity.

Spike S4 saw it accept records with leafHashes and merkleRoot deleted, with a crystal bit flipped and parity re-fixed, with chainId altered, and with residual bit flips that decode to the same bytes (3.5515% of single-bit flips of a residual; a re-encode check rejected 689 of 689). It rejects swapped frames. The Lexicon’s stricter importer is claim L10 (Explainer 4). In Phase 3, on 50 C0 packages of each class, Owl’s verifyIntegrity accepted 50 of 50 in each of T1 (leaves and root deleted), T2 (a crystal changed, parity re-fixed), T8 (chainId altered) and T9 (a residual flip that decodes the same), while the hardened importer rejected all 450 tampered packages, in JS and in Python (Explainer 11).

ATTEST/1 in two languages

Spike S7 ran BioChain-AI’s own attestation code in Node and checked it in Python. WebCrypto writes a signature as IEEE P1363 r‖s (64 bytes); Python’s cryptography expects DER. Python verified Node’s signatures 200/200 after conversion and 0/200 raw; the way back must left-pad r and s to 32 bytes. The high-S twin (r, n − s) also verifies, in WebCrypto, node:crypto and Python, so signatures are not unique and nothing may be keyed by signature bytes. (“~” timing: the whole attestation step, 0.2341 ms per shard in Node.)

The 60 KB lineage cap

A biochain grows by epochs. extendBiochain recreates the parent’s text, appends the new text and regrows the whole through growBiochain, which throws above 60,000 bytes. So the cap holds for a whole lineage, not only for one step. Corpus-scale language data must therefore be many independent shards tied together by a manifest. WordNet’s noun synsets make 148 shards (the registered set C0). Spike S4 extrapolates BabyLM strict-small (55 MB) to 918 shards and strict (550 MB) to 9,178. The manifest is an RFC 6962 Merkle tree (Explainer 4).

What follows

A namespace has to live above the word: a kind field in the stream or record header. The layout census asks SHD-CCP for one, and notes that BioChain-AI’s publishBiochain drops meta.kind today. The Lexicon does not wait: it names its data by record kind (chapter 6).

One bridge

Decision D7: the Blackwell word only at the Owl/BioChain bridge. What a piece of data is lives in record kinds above the word, never in a Form nibble.

Inside the LexiconNo tiles. Addresses are variable-length norm-5 words, with 59- or 64-bit ids up to 25 or 27 letters; points are exact rationals; records are JSON plus SHA-256.
Record kindsLVOCAB/1, LADDR/1, LPREP/1, LCORPUS/1, LGROW/1, LBENCH/1: typed commitments, pipe-joined like GROWN/1, signable as ATTEST/1.
The bridgeShards are unmodified shdccp/2 streams: the Blackwell word exactly as the pinned codec writes it, form-9 crystals only. No new form ever appears inside.

Why record kinds. No Form value is free (chapter 5), and the biochain document itself has no type field. Each Lexicon record carries {kind, spec: 'hyperbolic-lexicon/0.1', compat: 'biomesh-js'}, so a reader knows what it holds before it decodes anything: a vocabulary, an address table, a pre-processed shard, a corpus manifest, its growth, or benchmark receipts (Explainer 4).

Versioning

  • Shards keep streamVersion: "shdccp/2" and the JavaScript codec’s hashing (D8), so Owl’s and BioChain-AI’s verifiers accept them as they are.
  • Anything that changes bytes is only proposed, under a future shdccp/3: how to write the 0x80 byte, binary RFC 6962 leaves, mandatory leaves, root and crystal checks, a recomputed chainId, the exact weave, and a kind field.
  • The Lexicon’s own versions are the /1 of each record kind.

Claim L8 registers the bridge: language shards are Owl-valid biochains, field for field, in JS and Python. Owl Academy’s and BioChain-AI’s own JavaScript are the authority for compatibility (D9). Spike S4’s 126/126 is a spike result on verbs and adjectives; L8 was decided in Phase 3, on the 148 noun shards and 20 synthetic ones: supported, with 0 of 336 records differing from Owl’s in any field, for our JS grower and for our Python port (Explainer 11).

07

LPS p = 5: our tree is SHD-CCP’s overlay

The strongest link between the Lexicon and SHD-CCP is mathematical. The six generators of our address tree are exactly the Lubotzky–Phillips–Sarnak generators for p = 5. So the Ramanujan graphs X(5, q) that SHD-CCP’s RFC 03 plans as its peer-to-peer overlay are finite quotients of the same tree. (RFC 03 does not yet name LPS or its generators; the proposal below asks it to.)

Hyperbolic Oracles’ P.GENS are the integer quaternions 1±2i, 1±2j, 1±2k, each of norm 5. LPS take, for a prime p ≡ 1 mod 4, the quaternions of norm p whose first coordinate is odd and positive and whose other three are even. For p = 5 the only solutions are a first coordinate of 1 and one other coordinate of ±2: exactly these six, p + 1 of them. A reduced word never follows a generator with its own conjugate; the root has 6 children and every other node 5. A word of length L multiplies out to one integer quaternion of norm exactly 5L, and right division by the generators reads the word back exact. The Lexicon uses these words as training-free addresses for WordNet synsets (Explainer 3).

X(5, q), measured by spike S5

To build X(5, q), pick a prime q ≡ 1 mod 4 and a number ι with ι² ≡ −1 mod q. Then each generator becomes a 2×2 matrix mod q of determinant 5, and a word becomes the product of its matrices, taken up to a scalar (projectively). The Cayley graph has those matrices as vertices and joins two whenever one generator carries one to the other. Spike S5 built it for the three q of claim L7, on synthetic words only:

Each graph is 6-regular, connected and inverse-closed. The girth is the length of the shortest cycle. Up to radius r the graph looks like the tree, so distinct reduced words of length at most r land on distinct vertices, and collisions begin at r + 1. The eigenvalues come from numpy.linalg.eigvalsh in float64 float, cross-checked by exact power sums and by Lanczos; everything else is exact. The output reports “64/64 checks pass”. As “~” timings, eigvalsh took 2.6 s, 17.4 s and 161.2 s on this container, the last on a 1,131.8 MiB matrix.

SHD-CCP’s own arithmetic agrees

SHD-CCP’s HurwitzQuaternion works in doubled coordinates, so the generators are (2, ±4, 0, 0), (2, 0, ±4, 0) and (2, 0, 0, ±4). Spike S5 imported SHD-CCP’s hurwitz.py read-only. Its product, halved, equalled P.wordQuaternion on 1,000/1,000 words, and its norm was 5len on all of them; without the halving it never matched. The registered controls failed as they must: a wrong ι = 2 broke the walk on 968/1000 words at every q, a 4-generator subset gave a 4-regular graph, and the unhalved product disagreed. Claim L7 registers these checks, with these controls, on its own instances (one tree, three readings: address, H³ point and X(5, q) vertex). It was decided in Phase 1, not by the spike: supported, with no failure and every control failing (Explainer 9).

Exact Qh on the wire

RFC 03 defines a Ghost map into H³ with Qh = sinh² d, and lists an exact (integer or rational) representation of Qh on the wire as a TODO. For two points a, b on the hyperboloid, Qh = ⟨a, b⟩L² − 1, where ⟨·,·⟩L is the Lorentz inner product; for rational points it is a rational number. For points of the octahedral H³ tree, whose coordinates at depth n are integers over 7n (spike S1), it is N / 72(na + nb) for an integer N, so it can travel exactly as the pair (N, na + nb). exact The proposal SHD-CCP-RFC03-exact-Qh-and-LPS.md asks RFC 03 to name LPS p = 5 and adopt this form.

A shard key, never integrity

Reducing an address mod q gives a deterministic shard key: it tells which of the 2,184, 4,896 or 12,180 vertices, and so which node of an overlay, holds a synset. It separates only words of at most r letters (3, 3 and 4 at these q). It is never an integrity check. Cayley hashes on LPS graphs have known collision attacks (Tillich and Zémor, 2008; Petit, Lauter and Quisquater, 2008). SHA-256 stays the integrity primitive.

Where JavaScript and Python part

The Lexicon’s method needs Python and JavaScript to agree bit for bit. The working SHD-CCP does not always. Six cases follow: two where the deployed JavaScript and BioChain-AI’s Python reference differ, a float weave that a Python port reproduces only with care, one name shared by two structures, one check that cannot fail, and the runtimes’ Unicode versions. Each gives what the spikes measured and how it is resolved.

1 · crystallize and the byte 0x80

The JavaScript crystallize writes the 32-bit crystal raw, so a byte 0x80 stays, read as code −128. BioChain-AI’s Python pack() forbids −128: it writes −127 (0x81) and recomputes parity. For the bytes [75, 0, 7], with crystal codes [−72, −128, 99, 69], JavaScript writes 98B8806345000352 and the Python kernel 90B8816345000352.

On 63 shards (4,992 packets), the kernel’s packets differed from Owl’s on exactly the 70 with a 0x80 byte, only by −128 → −127 and parity. The normalised stream differed on 43 of 63 shards, exactly those with such a chunk. But merkleRoot, both weaves and chainId were unchanged on 63/63, and Owl’s verifyIntegrity accepted the normalised records 63/63. The reason: leaves and the weave are computed from chunk bytes, never from packet words. So chainId and merkleRoot do not commit to the packets, and a verifier must re-crystallize to check them.

Resolution. JavaScript is normative for shdccp/2, since every deployed record was grown in JavaScript. The Lexicon’s Python is to reproduce the raw word; spike S4’s raw port already matched Owl’s JS word on 4,992/4,992 packets. The BioChain-AI proposal asks its Python to write crystals raw as well, and to settle the case for good under shdccp/3; since leaves and weaves come from chunk bytes, writing raw changes no deployed chainId. L8’s first control is a Python grower with the kernel’s normalisation, which must differ from Owl’s record on at least one synthetic shard. In Phase 3 it differed on 20 of 20, in the stream only; 189 of C0’s 12,378 chunks (1.527%) have a crystal holding 0x80; and the Lexicon’s Python port, which writes the word raw, gave Owl’s record on 336 of 336 (Explainer 11).

2 · Leaf and Merkle hashing

The JavaScript hashes strings: leaf i = SHA-256(i + "|" + sha256Hex(String.fromCharCode(...chunk))), and a parent hashes its two children’s hex strings joined; an empty list’s root is SHA-256(“empty”). String.fromCharCode turns each byte into a code point, and SHA-256 then reads the UTF-8 of that string, so every byte from 0x80 up is hashed as two bytes. BioChain-AI’s Python codex_engine.py hashes binary instead, SHA-256(4-byte index ‖ SHA-256(chunk)), with 32 zero bytes for an empty root. Neither side can verify the other’s chains.

Resolution. Shards use the JavaScript rule (D8), and the Lexicon’s Python is to reproduce its quirk exactly. Spike S4 found the orbital core’s SHA-256 equal to Node’s over UTF-8 on 1,000/1,000 strings, and the JS-rule grower equal to Owl’s on 126/126 records. L8’s second control, a grower that hashes leaves over binary bytes, must differ on every non-empty shard; in Phase 3 it differed on 168 of 168, and Owl’s verifyIntegrity rejected all 168 (Explainer 11). Manifests use RFC 6962 instead, defined once and tested with vectors (L9).

3 · The float weave

The chiral weave renormalises with Math.hypot and prints with toFixed(12) float. A one-ulp difference at a rounding edge changes the string, and so chainId. Spike S4 compared Python ports with Owl’s JavaScript on 1,000 synthetic shards:

Python port of the weaveShards with any difference
Faithful: V8’s Math.hypot algorithm, exact toFixed(12)0 of 1000
Naive: Python’s math.hypot, format(x, '.12f')2 of 1000

The cause is hypot, not formatting: math.hypot differed from V8’s on 39,408 of 127,152 calls (30.9928%), while format and toFixed(12) differed on 0 of 8,000 weave components.

Resolution. The Lexicon’s Python port is to reproduce V8’s Math.hypot algorithm and toFixed(12) exactly, as L8 registers. For shdccp/3 it proposes the exact norm-5 weave instead: engram_core.chainQuaternion over the first 8 bytes of each leaf hash exact. Spike S4 checked it on one verb shard of 84 leaves: its norm is exactly 52352, its components have 2,729–2,730 bits, it unfolds to the leaf prefixes in order, and the 7 segment products multiply to it. Claim L9 tests it on every shard (Explainer 4). In Phase 3 the Python port matched Owl’s float weave on every record (L8), and all 148 C0 exact weaves were exact, with components of 971–2,731 bits, equal in JS and Python (L9(b); Explainer 11).

4 · Two structures called “Merkle”

The orbital core’s “Lemma 15 Merkle chain” is a linear backward chain: τN = H(GN), τd = H(Gd ‖ τd+1). Biochains use a binary tree with the last node duplicated on odd levels. They prove different things and are not interchangeable. The tree rule is also malleable: [a, b, c] and [a, b, c, c] build the same tree. Spike S4 showed this on real leaf hashes, and found that for K = 1..200 a list and the same list with its last element repeated have equal roots at every odd K ≥ 3 (99 values), but not at K = 1. RFC 6962 roots of the same lists were equal at 0 of 200.

Resolution. The two are named apart and never mixed. The Lemma 15 note proposes an RFC 6962 statement of Lemma 15 for SHD-CCP. L9’s first control is exactly this collision; in Phase 3 it occurred at K = 3, 7 and 1,001, while the RFC 6962 manifest detected every alteration (Explainer 11).

5 · An always-true continuity check

Owl Academy’s Engram Mind Eye computes each packet’s chained header as (fold32(seed64) ^ rotl32(prevParity, 1)) >>> 0 (line 872). Lines 889–890 then “check” it by recomputing the same expression from the same inputs and comparing. The check cannot fail, so it detects nothing.

Resolution. It is never reused as an integrity check. Engram Mind’s Eye does not rely on it; its integrity comes from SHA-256 and the Merkle chain. The Owl notes describe a real check: recompute the header from the stored previous packet and compare it with the stored current header.

6 · Unicode versions

Spike S6 swept every code point in three runtimes. Node 22.23.4 carries Unicode 17.0 (ICU 78.3), Chrome for Testing 153 behaves as Unicode 17.0, and Python 3.13.18 carries 15.1.0. Node and Python gave different general categories on 9,990 code points, and different lowercase, decomposition and combining-mark values on 55, 20 and 76; Node and Chromium agreed on all. On the 20,520 cases of the stress set, a normaliser built from the platform’s toLowerCase, normalize('NFD') and \p{Mn} differed from Python’s on 725, in Node and in Chromium alike. (These counts are “~” lines: they depend on the runtime versions.)

Resolution. D5: the normaliser runs on Unicode 15.1 tables exported from Python and pinned by SHA-256, fails closed on code points unassigned in 15.1, and never calls the platform’s functions. S6’s prototype table (142,041 bytes as compact JSON) reproduced Python’s lowercasing, Final_Sigma, decomposition and mark removal with 0 mismatches on all 1,112,064 code points alone and on 2,000 synthetic strings. Claim L1 tests the whole front end (Explainer 3).

Smaller ones

  • Two engram hex conventions. Engram streams write a key’s bytes least significant first (GEODESIC → 5C896A4801C9C24C); Owl’s Mind Eye packet writes seed64 byte-reversed (4CC2C901486A895C). Streams use the first; the Lexicon’s golden JSON is to pin both.
  • Two engram tokenizers. “don’t” becomes [DON, T] in Owl’s Engram Mind Eye and [don’t] in biomesh.js. The engram layer follows biomesh.js; the Lexicon’s tokenizer is a third, pinned one.
  • verifyIntegrity’s scope (chapter 3). The Lexicon’s verifier is a strict superset, claim L10.
  • The value laws differ between the JavaScript and the Python; they are reported only, never compared.

One thing already agrees: the survey found the order-2 rank coder’s unprimed residuals (no codex prior) bit-identical in the two languages.

Golden vectors

A golden vector is a fixed input together with its exact expected output, which every implementation must reproduce. SHD-CCP already has a format for them. The Lexicon proposes six suites in it.

The format. SHD-CCP’s golden vectors have two parts: a JSON envelope that validates against schema.json (suite, spec_version, rfc, status, description, generator, binary, cases), and a little-endian binary mirror: the magic SHDGEV01, a 32-bit field count F, a 32-bit record count N, then N×F 64-bit records. Values above 253 are strings in the JSON. The suites are regenerated byte for byte and CI fails on drift. Today they hold 2,366 cases:

Two constraints. Every suite that is not pending needs a binary object, so only fixed-width records fit SHDGEV01. Variable-length data (tokenizer outputs, address words of varying length, whole shards, exact points with hundreds of bits) cannot go in the binary mirror. It stays in the Lexicon’s own golden JSON, as Engram Mind’s Eye keeps its E1 corpus, and enters SHDGEV01 only as the four 64-bit limbs of a SHA-256.
