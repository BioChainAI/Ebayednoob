01

Where this sits

The pins and the spikes feed the preregistration, and the preregistration feeds the Python reference and the browser core that will decide every claim. This page’s focus node is the preregistration.

Phase 0 is analysis, seven measurement spikes and a preregistration; there is no model code. The spikes have finished. Each script and its captured output sit in spikes/, and every spike number on this page comes from those outputs and is called a spike result (“spike S3 measured …”); in the claims table, spike numbers appear as the preregistration rounds them. The claims are summarised from PREREGISTRATION.md, the authority on what each claim says; where this page and that file differ, the file wins.

The grey blocks copy output lines exactly, chosen and shortened by leaving lines out, never by editing one. Lines that begin with “~” carry timings and runtime versions, which change from machine to machine. They are never quoted in a block, and where the prose uses one, it says so.

How to read this page

A spike result is a measurement on data no claim uses. It decides nothing. A claim is registered with its instances, controls, decision rule and prediction. Phase 1 decided four (L2, L3’s Python side, L5, L7), Phase 2 three more (L1, L3(f), L4(a, b)), Phase 3 four (L8–L11) and Phase 4 two more (L6, L4(c)); all are supported. A prediction is not a decision: “predicted refuted” means the registered prediction, fixed in advance, expects the test to come out that way. L6(c) was predicted refuted and came out supported (Explainer 12).

exact: integers, rationals or bytes, identical in every engine. float: floating point, rounded at every step.

Spike
A short measurement script run before the claims were written, to fix a fact the design depends on. Each has a header (what it measures, how to run it, what it settles, its data and seeds) and a captured output ending in a SETTLES block.
Preregistration
Writing down, before any code that tests a claim exists, what will be tested, on which data, how it will be decided and what is expected.
Instance
The registered data a claim is decided on, such as all 82,115 WordNet noun synsets.
Control that must fail
A deliberately broken variant of a test. It must show its weakness on at least one case. If it passes, the test cannot tell good from bad: it is void, and is repaired by amendment.
Decision rule
The rule, fixed in advance, that turns a result into supported, refuted or inconclusive. Exact claims are all-or-nothing: one failure refutes, and is recorded as a counterexample.
Dry run, decisive run
A dry run exercises a runner on unregistered seeds and data. The decisive run is the one that decides, on the registered instances.
MAP
Mean average precision. For each query node, rank every other node by distance and measure how high its true neighbours come; average over queries; 1 is perfect. Graph-edge MAP counts the parent and the children as neighbours; closure MAP counts every ancestor and descendant.
Pessimistic ties
When a neighbour and a non-neighbour are exactly equally far, the neighbour ranks after. This is the registered rule; optimistic values are shown only for contrast.
Virtual letters
Under the address rule a node with c children gives each child m = max(1, ⌈log₅ c⌉) letters. With more than 5 children, each child gets two or more letters (up to 4 in the verb forest; under the noun with 659 children, 5), and the letters beyond the first stand for no WordNet node (Explainer 3).
02

The order of Phase 0

Phase 0 ran in a fixed order, so that no case a claim is decided on could have shaped the claim.

  1. Pin the data. WordNet 3.0 and UD English EWT are fixed by hash and count, fetched once into a cache outside git (chapter 3). The nouns, which most claims are decided on, were touched only to count and hash them: the metadata needed to define the instances.
  2. Run the spikes. Seven scripts, each with its captured output, on data disjoint from every registered instance: WordNet verbs and adjectives, Owl Academy’s canon tree, synthetic words, repository Markdown and full Unicode sweeps. Their seeds are 90000 + i, which no later run may reuse. They decide no claim.
  3. Register the claims. PREREGISTRATION.md, registered 2026-11-05, was committed alone, before any code that tests the claims exists. It holds L1–L11, the design inputs D1–D12, the common rules and the shared instances.
  4. Then everything else: the hub, the eight explainers (this page among them), the README, the proposals, the tests and the summary.

Why spikes come first

A design rests on facts nobody has measured yet: how deep float64 stays correct, which boost makes an H² tree decodable, how long WordNet’s addresses get. Measured on the registered instances, they would be circular: the claim would be fitted to the cases that decide it. So each spike measured its fact on disjoint data, and the claims were written afterwards, against instances no spike had touched except to count or hash them.

The preregistration puts it this way: the spikes “fixed facts the design depends on, and three of their values are written into this file where marked (S3 in L6(c), S4 in L8 and L10, S6 in L1). They decide no claim.” Other spike results appear in the predictions, as expectations, never as findings.

An example: L6(c)

The design fixed a rule before spike S3 ran: L6(c)’s prediction would read “supported if S3’s exact-tree graph-edge MAP on verbs is ≥ 0.90, otherwise refuted” (the rule is quoted in S3’s own header). S3 measured 0.6309, so the registered prediction reads refuted. The claim was decided in Phase 4, on the mammal closure, against learned embeddings (chapter 7), and came out supported: the prediction was wrong (Explainer 12).

After Phase 0: dry runs, then the runner, then the decisive run

From Phase 1 on, every runner follows Engram Mind’s Eye’s discipline. It is first dry-run on unregistered seeds and on the dry-run data each claim names (the verb forest, repository Markdown, synthetic shards). Then the runner is committed. Only then comes the decisive run on the registered instances. Engram ran its first nine claims this way on 2026-11-04, with the runner committed beforehand (its evidence page).

S1 · The H³ tree, exact against float

s1_h3_tree_metrics.cjs · output. The H³ tree gives every word an exact point. How deep can float64 go before it ranks or decodes those points wrongly, and what do exact points cost?

The method. All on TreeEmbedding3D as it is, with the boost t = 3/4: cosh τ = 25/7, sinh τ = 24/7, τ = ln 7. A word of length n is a point whose coordinates are integers over 7ⁿ. The spike measured exact distances between relatives; how often hyperbolic distance reverses tree-distance order on the 937 words within 4 letters of the root; graph-edge MAP on small subtrees, some with virtual letters; and, at each depth 1–40, the ranking of 21–26 nearby candidates (parent, grandparent, siblings, uncles, children and some grandchildren) exactly and in three float modes. It also measured the bit cost of exact points up to depth 60. Words come from Rng(90000 + n); the straight word always takes child 0, a geodesic, and float64 ranking inverts on it first.

  parent-child                               [0] [0,0]: cosh d = 25/7, d = 1.9459
  siblings at 90 deg (straight vs bent)      [0,0] [0,2]: cosh d = 625/49, d = 3.2375 (law of cosines with cos theta = 0: equal)
  siblings at 180 deg (bent +y vs bent -y)   [0,2] [0,3]: cosh d = 1201/49, d = 3.8918 (law of cosines with cos theta = -1: equal)
  total: 2264600 comparisons, 47352 reversed (2.09%), 0 tied (0.00%); first source recounted with direct Q comparisons: equal

Children 1–4 leave at 90°, so a bend shortens a two-edge path by 0.6543, a loss that tends to ln 2 for long edges. Hyperbolic distance is therefore not tree distance. It reversed tree-distance order in 2.09% of comparisons, never across a gap of more than two hops.

Float against exact. Each row reads: among 20 random words of length n, how many rankings invert an exactly strict order / fail (invert, tie or a non-finite float32 product) in three modes: point(), the float placement; f64 exact, the exact point rounded once; and f32. Then the straight word’s status, and how many of 50 words float decoding returns.

    n=10  random  0/ 0 |  0/ 0 | 20/20   straight inv | inv | tie   decode random 50/50 | 50/50, straight ok | ok
    n=12  random  3/ 4 |  1/ 2 | 20/20   straight inv | tie | tie   decode random 50/50 | 50/50, straight ok | ok
    n=13  random 14/15 | 13/14 | 20/20   straight tie | tie | tie   decode random 49/50 | 49/50, straight ok | ok
    n=15  random 20/20 | 20/20 | 20/20   straight tie | tie | tie   decode random 24/50 | 29/50, straight ok | ok
  first depth with an inversion, random words: f64 point() 12, f64 exact 12, f32 5
  first depth with an inversion, straight word: f64 point() 10, f64 exact 10, f32 5
  first depth at which float decode fails, random words: point() 13, rounded exact 13
  decodeExact(pointExact(w), n) returned the word on 840/840 ranked words; the adjacent-level and all-pairs inversion tests agreed on every ranking
- Bit budget: at depth 28, <= 139-bit numerators (random), 157 (straight) and 79-bit denominators (7^28); at depth 60,
  297 / 336 / 169. Every coordinate at depth n is an integer over 7^n and every Lorentz product an integer over 7^(n_a + n_b),
  so ranking by an integer key is exact.
- Graph-edge MAP with pessimistic ties: perfect 5-ary subtree of depth 3 = 1/1 (0 neighbour/non-neighbour ties);
  root with 25 children (m = 2) = 0.995703; root with 125 children (m = 3) = 0.995276; 25-ary at every level (m = 2) = 0.260362
  (optimistic 0.845473). Neighbour/non-neighbour exact ties appear only with virtual letters (25, 120 and 525 queries):
  the virtual-letter tie effect behind the doubt in L6(c).

What it settled. Ranking must be exact. Float64 first inverts an exactly strict order at depth 10 on the straight word and 12 on random words, and fails on all 20 random words from depth 15. Float32 inverts from depth 5 and overflows from 23. Float decoding first fails at depth 13 on random words; exact decoding never failed. At depth 28 exact points need at most 139-bit numerators on random words (157 on the straight word) over 79-bit denominators, and every Lorentz product is an integer over a power of 7, so ranking by an integer key is exact. Exact ties between a neighbour and a non-neighbour appear only where virtual letters occur. On this container an exact point at depth 28 took about 1.6 ms against 3 µs in floats (a “~” line).

What it informs. L3’s control 3 (float decoding must fail beyond 12 letters); L4(b) and both L4 controls (float32 inverts; a float evaluator with index tie-breaking differs where exact ties exist); the bit budget in L3’s report; and the tie effect behind L6(c) (exact ranking in Explainer 3).

S2 · An exact H² tree

s2_h2_exact_tree.cjs · output. No exact tree existed in the hyperbolic plane: the old one is built from cos and sin. Which rational boost lets greedy decoding recover every word exactly, and what does it cost against H³?

The method. The tree uses only rational directions: (1, 0), (3/5, ±4/5), (−7/25, ±24/25) and (−1, 0), at 0°, ±53.13°, ±106.26° and 180°. Each step rotates, then boosts with cosh + sinh = m, so τ = ln m and t = (m − 1)/(m + 1). For m ∈ {3, 5, 7, 12, 19, 20} (and 8–11 as a supplement) it decoded 500 random words per depth exactly, checked the sheet identity x₀² − x₁² − x₂² = 1 exactly on every point, computed every point a second way in BigInt, counted bits, and swept float64 decoding.

  depth              2    4    6    8   10   12   16   20   24   28
  m=3  t=1/2       303  105   23    7    4    1    0    0    0    0
  m=7  t=3/4       500  443  376  311  274  226  148  124   84   55
  m=12 t=11/13     500  500  500  500  500  500  500  500  500  500
  m=20 t=19/21     500  500  500  500  500  500  500  500  500  500
  H^3 t=3/4        500  500  500  500  500  500  500  500  500  500   (decoder3d decodeExact, octahedral tree)
  exact ties among the best-scoring children: 0 in 390000 greedy decisions (none happened)
  planning replay, Rng(90001): 100 words at depth 12 then 40 at depth 28 from the same stream: t = 11/13 100/100 and 40/40; t = 3/4 48/100 and 1/40

Why some m fail: greedy decoding picks the child direction nearest the point, so each child’s whole subtree must stay within the bisector between neighbouring directions (26.57°). The spike measured each subtree’s exact half-width seven levels down.

  margin to the bisector at 7 levels (a lower bound on the half-width, so an upper bound on the margin): m=10 2.01 · m=11 6.00 · m=12 8.72 · m=19 16.96 · m=20 17.54 degrees
  range of the per-coordinate ratios at t = 11/13 over the four classes: 1.28x .. 2.38x
  worst over all classes at depth 28: H^2 t = 11/13 251/188 bits, H^3 157/79 bits (1.60x, 2.38x)
  - float64 (same construction) at t = 11/13 keeps 500/500 up to depth 8 and reaches 0/500 at depth 20; exact rationals are required beyond that.

What it settled. D3’s boost, t = 11/13 (cosh 145/24, sinh 143/24, τ = ln 12): 500/500 at every depth from 2 to 28, with no exact ties. The threshold lies between m = 9 and 10. m = 10 and 11 decode as well, but m = 12 keeps the widest margin of the three (8.72° against 2.01° and 6.00°) and the fewest bits at depth 28 (225/152 against 247/185 and 235/167). The H³ boost t = 3/4 in the plane decodes only 226 of 500 words at depth 12. The H² tree costs 1.28×–2.38× the bits of H³ per coordinate at depth 28. The S2 replay also reproduced the design’s earlier planning check (100/100 and 40/40 at t = 11/13; 48/100 at t = 3/4).

What it informs. D3; L3(e) in H² and L3’s control 4 (the H² tree at t = 3/4 must fail); the bit cost of L4’s H² ranking (placement in Explainer 3).

S3 · WordNet’s shape, on verbs

s3_wordnet_shape.cjs and .py · output. Under the address rule, how long do WordNet-shaped words get, and how well does the exact H³ tree rank a real hierarchy?

The method. The nouns are the registered instances, so the spike used the verb forest: 13,767 synsets with 559 roots. The roots were read as children of a virtual root at the word [1], 4 letters each. It also used Owl Academy’s canon tree (169 nodes: canon, 10 departments, 13 artifacts, 145 tomes). On each it applied the L3 rule, computed every exact point, and ranked every query against every other node by the exact Lorentz product, as integers. Then it computed graph-edge and closure MAP with pessimistic ties, over all 13,542 verb queries. S5 · The LPS overlay X(5, q)

s5_lps_overlay.py · output. SHD-CCP’s RFC 03 plans Ramanujan graphs X(5, q) as an overlay. Our tree’s six generators, 1±2i, 1±2j, 1±2k, are exactly the Lubotzky–Phillips–Sarnak (LPS) set for p = 5. Is X(5, q) then a quotient of the tree our addresses live on, and what are its facts?

Terms. For a prime q with 4 | q − 1, pick ι with ι² ≡ −1 (mod q). The LPS map φq sends a quaternion to a 2×2 matrix mod q. Matrices equal up to a nonzero scalar are one vertex, and each vertex is joined to its products with the six generator matrices: a Cayley graph. Its girth g is its shortest cycle, so words of length up to r = ⌊(g − 1)/2⌋ cannot collide. It is Ramanujan when every eigenvalue other than ±6 has |λ| ≤ 2√5 = 4.4721.

The method. In Python with numpy, for q = 13, 17, 29: build each graph by breadth-first search from the identity and check its size, 6-regularity, inverse closure and bipartiteness. Compute the girth exactly three ways and test every reduced word up to length r. Reduce 1,000 synthetic words’ quaternions mod q and compare each with walking the word. Take the dense eigenvalues, checked by power sums and Lanczos, and multiply the generators with SHD-CCP’s own HurwitzQuaternion. Three controls must fail.

  - q = 13: iota = 5, (5|13) = -1; 2,184 vertices = |PGL(2,F_q)| = q(q^2-1), bipartite, 6-regular, connected, inverse-closed, diameter 7; exact girth g = 8, so r = 3; largest nontrivial |lambda| = 4.249721, Ramanujan margin 0.222415 to 2 sqrt 5 = 4.4721.
  - q = 17: iota = 4, (5|17) = -1; 4,896 vertices = |PGL(2,F_q)| = q(q^2-1), bipartite, 6-regular, connected, inverse-closed, diameter 9; exact girth g = 8, so r = 3; largest nontrivial |lambda| = 4.308919, Ramanujan margin 0.163217 to 2 sqrt 5 = 4.4721.
  - q = 29: iota = 12, (5|29) = +1; 12,180 vertices = |PSL(2,F_q)| = q(q^2-1)/2, not bipartite, 6-regular, connected, inverse-closed, diameter 8; exact girth g = 9, so r = 4; largest nontrivial |lambda| = 4.442016, Ramanujan margin 0.030120 to 2 sqrt 5 = 4.4721.
  - L7(e): P.wordQuaternion = HurwitzQuaternion product of (2, +-4, 0, 0), (2, 0, +-4, 0), (2, 0, 0, +-4), halved (1,000/1,000 words); without halving it never matches.
  - L7 controls fail as required: iota = 2 breaks the walk identity at every q; the 4-generator subset is 4-regular; the unhalved Hurwitz product disagrees.

L6(c), predicted refuted, found supported

The prediction was fixed by a rule set with the design: “supported if S3’s exact-tree graph-edge MAP on verbs is ≥ 0.90, otherwise refuted”. S3 measured 0.6309, an exact 205-digit rational reproduced by an independent Python recomputation, so the prediction reads refuted. The cause is the virtual letters: siblings that share a virtual prefix sit as close as the parent or closer. The decision was made in Phase 4, on learned Lorentz embeddings at d = 3 on the mammal closure, five seeds, by the rule in the table, and it went the other way: the exact tree’s graph-edge MAP is 0.690653 against 0.458–0.477, and every (exact − learned) interval’s lower end is at least 0.19, so (c) is supported. The rule assumed that learned embeddings keep graph edges; trained on the closure, they rank ancestors and descendants alike, and direct parents and children reach only about 0.46. The prediction was wrong, and it stays on record (Explainer 12).

Predictions against the system

Not every prediction is flattering. L6(c) expected the training-free tree to lose to learned embeddings on graph-edge MAP (in Phase 4 it won instead, so that prediction was wrong), and L5 expects it to fall short of Sala et al.’s combinatorial 0.989 in 2 dimensions at about 500 bits (verified; reported, not part of L5’s decision). Hyperbolic Oracles’ C1, “hyperbolic beats flat” for optimisation, was refuted (Explainer 1), and every hyperbolic claim here has a matched Euclidean or flat control.

What none of this decides

The preregistration ends its claims with what they leave open. The spikes leave open more still, because they ran on other data.

What the preregistration does not decide

  • Whether hyperbolic geometry helps a language model. Stage-2 claims (lexical semantics), Stage-3 claims (small MLM pretraining on BabyLM) and Stage-4 claims (GLUE, MTEB) are registered by amendment before any code for them, and most need a wider network or a GPU (Explainer 7).
  • Whether the norm-5 address carries meaning beyond WordNet’s spanning tree. One address per synset is one sense, without context; ## pieces get orthographic addresses.
  • Whether SHD-CCP’s maintainers adopt any proposal in proposals/ (Explainer 2).

What the spikes cannot decide

  • Any claim. They ran on disjoint data: the verb forest, not the nouns; synthetic words, not WordNet addresses; verb and adjective glosses, not C0; repository Markdown, not glosses or EWT. A spike value is a fact about that data, and none is a finding of a registered test.
  • The noun MAP. S3’s 0.6309 is on verbs, read under a virtual root. The nouns have one real root, depth 19 and up to 659 children. L6(c)’s prediction follows from the rule; its decision was made on the mammal closure, in Phase 4, where (c) is supported, against the prediction (Explainer 12).
  • L4(b) on WordNet. S1’s float depths come from random and straight synthetic words with 21–26 nearby candidates each. L4(b) was decided on 1,000 noun queries against all 82,115 candidates, in Phase 2: float64 inverts an exactly ordered pair in 997 of them (Explainer 10).
  • The real grower and importer. S4’s grower was spike-only, and S7’s commitment carried placeholder hashes. L8–L10 tested the Phase 3 code on C0, and all three are supported (Explainer 11).
  • Exact spectra. S5’s eigenvalues are float64, checked by power sums against exact walk counts. L7(d) asks for a margin of at least 10−9; the smallest S5 found, at q = 29, is 0.030120.
  • Tomorrow’s runtimes. S6’s divergences and its 725 depend on the runtimes’ Unicode versions (“~” lines); an update to Node or Chrome moves them. The stress set is fixed by its hash, and the pinned tables are meant to keep the platform’s Unicode out of L1.
  • Timings. “~” lines belong to this container (4 CPU cores). L11 was decided on its own timed runs, in Phase 3: a median 155.4 ms per full C0 shard, on packages grown with engrams off, a reading Amendment 8 fixed after the dry runs (engrams-on packages: 243.6 ms, reported; Explainer 11).
